1

GCP 인바운드 프록시 + WireGuard 터널

ℹ️ 백엔드는 집PC Docker에서 돌고, GCP는 외부 인바운드를 받아 터널로 넘기는 "현관" 역할만 합니다. 외부에서 api.samba-wave.co.kr로 들어온 요청을 GCP 정적IP + Caddy가 받아 WireGuard 터널을 통해 집PC 컨테이너로 전달합니다.
1
GCP 정적 외부 IP 확보
인바운드 진입점이 될 고정 IP를 예약합니다. 이 IP에 도메인 A 레코드를 연결합니다.
2
GCP에 Caddy 리버스프록시 구동
정적IP의 인스턴스에서 Caddy가 HTTPS를 종단하고, 터널 너머 집PC samba-api로 reverse_proxy 합니다.
# GCP Caddyfile — 터널 너머 집PC 컨테이너로 전달
api.samba-wave.co.kr {
  reverse_proxy (WireGuard 터널 내 집PC samba-api 주소)
}
3
WireGuard 터널 구성 (GCP ↔ 집PC)
GCP 정적IP 측과 집PC 측에 WireGuard 피어를 설정해 양방향 터널을 만듭니다. 집PC 측 WireGuard 컨테이너는 deploy/local/docker-compose.tunnel.yml 에 포함되어 함께 기동됩니다.
📌 EMS(ESMPlus) 등 일부 마켓 아웃바운드는 터널을 통해 GCP 정적IP를 출구로 사용합니다. 터널이 끊기면 인바운드뿐 아니라 이 아웃바운드 출구도 영향을 받습니다.
2

집PC PostgreSQL 컨테이너 구동
deploy/local/docker-compose.tunnel.yml 에 PostgreSQL이 포함되어 있어 스택과 함께 기동됩니다.

2
DB 사용자 및 데이터베이스 확인
컨테이너 환경변수로 사용자/DB가 생성됩니다. .env 값과 일치하는지 확인
📋 확인할 항목

집PC Docker 환경 설정

1
집PC 사양 권장
백엔드 + 워커 + DB + 터널을 상시 구동할 PC
권장 사양8코어 / 31GB RAM 이상
OSWindows 11
필수 설치Docker Desktop
구성 파일deploy/local/docker-compose.tunnel.yml
전원/네트워크상시 켜짐 + 안정적 인터넷 필요
2
Docker Desktop 설치 및 실행 확인
집PC에 Docker Desktop을 설치하고 실행 상태로 둡니다 (PowerShell에서 작업)
# Docker 설치 확인
docker --version
docker compose version
3
.env 파일 생성
deploy/local 의 환경변수 파일 작성
# deploy/local/.env

ENVIRONMENT=production

# DB (같은 Docker 네트워크의 집 PostgreSQL 컨테이너)
WRITE_DB_USER=samba-user
WRITE_DB_PASSWORD=(집 PostgreSQL에 설정한 비밀번호)
WRITE_DB_HOST=postgres
WRITE_DB_PORT=5432
WRITE_DB_NAME=samba-wave

READ_DB_USER=samba-user
READ_DB_PASSWORD=(위와 동일)
READ_DB_HOST=postgres
READ_DB_PORT=5432
READ_DB_NAME=samba-wave

DB_SSL_REQUIRED=false
JWT_SECRET_KEY=(openssl rand -hex 32 로 생성한 값)
SAMBA_INVITE_CODE=(openssl rand -hex 12 로 생성 — 본인만 아는 회원가입 비번. 미설정 시 가입 전면 차단)
AWS_EC2_METADATA_DISABLED=true

WireGuard 터널 설정 파일 배치
GCP 정적IP 측과 페어링되는 WireGuard 키/설정을 집PC 터널 컨테이너에 연결합니다 (docker-compose.tunnel.yml에 포함)
📌 인바운드: api.samba-wave.co.kr → GCP 정적IP/Caddy → WireGuard 터널 → 집PC samba-api. 터널 설정이 맞아야 외부에서 접속됩니다.

집PC 재배포 스크립트 설정

⛔ deploy/deploy.sh (옛 GCE VM 배포)는 폐기되었습니다 — 절대 실행 금지. 멈춘 GCP에 배포돼 무의미합니다. 재배포는 집PC에서 deploy/local/deploy-local.ps1 로만 합니다.
1
deploy/local/docker-compose.tunnel.yml 확인
집 PostgreSQL + WireGuard + samba-api + samba-worker + samba-reconciler 컨테이너 구성
# docker-compose.tunnel.yml 구성 컨테이너
postgres     # 집 PostgreSQL (진실 source)
wireguard   # GCP 정적IP와의 터널
samba-api   # gunicorn -w1: HTTP 서빙 + 오토튠 + 주문폴러
samba-worker # gunicorn 다중 워커: 마켓 전송 전담
samba-reconciler # gunicorn -w1: 주기 유지보수 루프 전담
2
deploy/local/.env 값 확인
3단계에서 작성한 DB·JWT·초대코드 값이 채워졌는지 확인
3
GCP 측 Caddyfile 도메인 확인
인바운드를 받는 GCP 정적IP 인스턴스의 Caddyfile (롤백용 백업은 Caddyfile.gcp.bak)
# GCP Caddyfile — 본인 도메인으로 교체
api.samba-wave.co.kr {
  reverse_proxy (WireGuard 터널 내 집PC samba-api 주소)
}
4
라이브는 빌드된 이미지로 구동
소스 볼륨마운트 없음 · --reload 없음. 백엔드 .py 변경은 반드시 재빌드해야 반영됩니다.
⚠️ "컨테이너 재시작만 하면 반영" 아닙니다. 재시작=옛 이미지 재사용 → 변경 미반영. 코드 변경 후에는 반드시 deploy-local.ps1 로 이미지(local-samba-api)를 다시 빌드해야 합니다.

🔧 문제가 생겼을 때

Q. 백엔드 코드 고쳤는데 반영이 안 됨
→ 라이브는 빌드된 이미지(local-samba-api)로 돕니다. 컨테이너 재시작만으로는 옛 이미지가 재사용됩니다. 반드시 cd deploy/local; .\deploy-local.ps1 로 재빌드하세요.
Q. deploy-local.ps1 실행 실패 (Docker 미실행)
→ 집PC에서 Docker Desktop이 실행 중인지 확인: docker compose version
Q. 헬스체크 실패 (DB 연결 오류)
→ 집PC에서 docker compose -f deploy/local/docker-compose.tunnel.yml logs postgres 로 집 PostgreSQL 상태 확인. .env의 DB 호스트가 postgres 인지 확인.
Q. 외부 HTTPS 접속 불가 (인바운드 끊김)
→ 도메인 DNS가 GCP 정적IP를 가리키는지 확인. GCP Caddy 상태와 WireGuard 터널 연결(GCP↔집PC)을 확인. 집PC가 켜져 있고 인터넷에 연결돼 있는지 확인.
Q. 집PC 컨테이너 상태 확인
→ docker compose -f deploy/local/docker-compose.tunnel.yml ps 및 docker compose -f deploy/local/docker-compose.tunnel.yml logs -f samba-api
Q. 마이그레이션 실패 — LockNotAvailableError (alembic_version 잠금)
→ idle in transaction 연결이 alembic_version 테이블 lock을 잡고 있는 것.
1. kill_idle.py: asyncpg.connect → pg_terminate_backend WHERE state='idle in transaction'
2. sudo docker cp kill_idle.py samba-samba-api-1:/tmp/kill_idle.py
3. sudo docker exec samba-samba-api-1 /app/backend/.venv/bin/python /tmp/kill_idle.py
4. remaining=0 될 때까지 반복 후 deploy-local.ps1 재실행
⚠ docker stop 절대 금지
Q. 배포 후 503 / DB connection pool 고갈
→ pg_stat_activity 확인. pool_pre_ping=False 설정 확인 (asyncpg 버그 대응). write pool 최대 40개, read pool 최대 15개 한도 확인.
